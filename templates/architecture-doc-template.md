**状态枚举（四档，权威定义）**

本节是 `状态` 列取值的**唯一权威定义**：技能 `SKILL.md`、模块模板与审查提示词一律引用本节，不再各自复述取值含义。四个取值就是全部取值。

| 取值 | 含义 | 谁设置 | 是否终态 |
|------|------|--------|----------|
| `待提供` | 提供方模块尚未设计，本条是对它的需求输入 | 调用方落盘时写入；架构总纲首轮由总纲前向登记 | 否 |
| `待调用方` | 提供方模块**已设计**、而调用方模块尚未落盘。缺口的认领方是那个尚未落盘的调用方模块，所以它**不是**「缺口没人认领」 | 提供方翻牌时写入 | 否（调用方落盘时改判） |
| `已落地` | 双方都已设计，且所提供的类/函数/变量在硬约束上与调用方的期望一致 | 提供方翻牌时写入 | 是 |
| `有差异` | 双方都已设计，但硬约束对不上（函数名、入参、返回类型或边界语义不一致） | 提供方翻牌时写入 | 否（用户裁决后收口） |

`不适用` 是**章节级**标记（章节确实不适用时保留标题并写「不适用：<原因>」），不是本表的状态取值。

**填表规则**

**状态只在本表维护。** 模块文档第 4 节只写需求与签名，不写状态——状态会因别人的落盘而变化，
放在一处就不会出现两处对不上。本表的状态分三段收口：

1. **调用方产生** —— 调用方模块落盘时写入本条，状态 `待提供`，并在变更清单中提示用户后续单独讨论提供方模块。
   架构总纲**首轮**落盘时所有模块都未设计，此时矩阵行由总纲前向登记、状态一律 `待提供`
   （该行表达的是架构层面**已经决定**的依赖，不是对某个模块的越权设计）
2. **提供方翻牌** —— 提供方模块落盘前读盘时看到指向自己的 `待提供` 条目，视为对它的输入需求，设计时**必须逐条处理**：
   调用方**已落盘** → 硬约束一致改 `已落地`、不一致改 `有差异` 并列出差异；
   调用方**尚未落盘** → 改 `待调用方`（合法终态，不是漏处理）。
   软约束（参数具体类型、错误类型体系、内部结构）由提供方自行决定，不影响状态
3. **裁决者收口** —— `有差异` 由用户裁决后，按裁决结果改调用方或提供方的文档，两边对齐后状态改 `已落地`；
   若任一方暂时无法修改，保持 `有差异`，并在两边的「待定问题与风险」各留一条说明。
   `待调用方` 在调用方模块落盘时由调用方改判为 `已落地` 或 `有差异`。

**`详见` 列指向调用方模块文档第 4 节**（那里是签名权威）。调用方尚未落盘时该列写
`待调用方落盘`，**不得**指向一个尚未存在的路径——引用必须可解析；调用方落盘后改为真实相对路径。

任何情况下都不得把提供方已经处理过的条目留在 `待提供`——那意味着这个缺口没人认领。

第 1、2 段只动本表，不碰任何模块文档。第 3 段需要改模块文档时，**用户裁决本身就是授权**，
可以改；没有裁决就不得擅自改动对方的模块文档。

## 10. 全局功能流程

<只画**方向级骨架**（服务功能点 + 触发入口 + 模块级调用链与每跳承担的核心类 + 每跳数据形态 + 结果落地 +
失败处理，六件事的逐项含义见下），不写模块内部细节——模块内的函数级调用链写在各自模块文档的第 5 节。
每条流程讲清六件事：服务功能点（这条流程服务于第 5 节的哪个或哪些功能点）
→ 触发入口（外部请求 / 上游调用 / 定时任务 / 事件订阅）
→ 模块级调用链（哪个模块在跨边界处调用了哪个接口，每一跳由哪个核心类承担）
→ 每跳的数据形态（模块之间传的是什么结构）
→ 结果落地（整条流程跑完最终产出什么、落到哪里、返回给谁）
→ 失败处理（哪一跳会失败、失败后整条流程如何收场：补偿 / 回滚 / 降级 / 直接上报，
错误最终由谁感知）。模块内部的失败细节归各模块文档第 5 节，这里只写跨模块层面的收场方式。

**服务功能点**：本节每条流程都必须写明它服务于第 5 节的哪些功能点，与第 5 节「对应流程」列
**两个方向都要对齐**——第 5 节每个功能点至少被本节一条流程服务；反过来，本节每条流程至少服务一个功能点，
两边对不上就是缺陷。

**全部功能流程都要登记**：系统的每一条功能流程都必须出现在本节，**包括模块级调用链只涉及一个模块的**——
单模块功能流程同样要登记、同样只写方向级，不得因为不跨模块就省略。

**只写方向级**：本节不描述模块内部的函数级调用链，只写模块级调用链以及每一跳承担的核心类；
函数级细节归各模块文档的端到端业务流程（第 5 节）。

流程名的对齐关系：本节登记的每条**功能流程**都要在参与模块文档的第 5 节里出现且同名，
跨边界跳在参与模块文档第 5 节里按同一流程名展开到函数级；反过来，纯属模块内部**实现**细节
（不是功能流程）的流程只写在模块文档，不要求登记到本节。

**每条流程都要配图**：本节登记的每一条流程都必须配一张图（登记了却没有随文档落盘的 SVG 图、**且未按占位形态写明原因**的流程判定为缺陷），图类型按其流程性质选定，不得按作者偏好任意挑：
- 描述系统整体结构（组件、服务、数据库、云资源、安全边界）→ 架构图
- 描述不同责任方或阶段的分工、含审批门与异常分支（泳道）→ 工作流图
- 描述谁调用谁、什么顺序、每步返回什么（API 调用链、缓存回源、鉴权检查）→ 时序图
- 描述数据从哪来、经过哪些处理、存到哪去，或需标出敏感数据边界 → 数据流图
- 描述状态迁移、重试、等待与终态 → 生命周期图

**图示与出图约定**：图由 `brainstorming-archify` 在文档落盘**前**先经**绘图规划 Gate** 确认（要哪些图、各是什么图类型、落在哪一节），确认后**先写 IR 并跑 `validate`**（validate 不写盘，只判定通过与否）**把图写进变更清单**（列出图名、图类型与落点，未通过校验的标 `未通过校验`），**待变更清单门批准后**再由内置绘图内核 `scripts/diagram-engine/bin/render.mjs` 一次产出三件套，与文档同批落盘；**人类作者不手写 IR**（IR 由 `brainstorming-archify` 从本节已有内容生成）。**图上不得出现本节正文没有的组件、参与者或状态**——若图确实需要它（例如本节要画的存储或外部系统在正文里还没写），先把该事实补进本节正文，再出图。落盘与引用形态固定如下：
- **落点硬规则**：设计文档落 `<项目根>/specs/design/`；全部图（三件套）落 `<项目根>/specs/design/diagrams/`，与设计文档同根——**不允许**放到项目根 `diagrams/` 或其他位置
- 每张图产出**三件套**，同目录、同前缀、扩展名不同，**不允许拆散存放**：`<文档序号>-<图名>.<图类型>.json` / `.svg` / `.html`（序号取**归属文档**：跨模块流程归架构总纲，即 `01-`；**只在单个模块内完成的功能流程，即使按规定登记在本文档第 10 节，也用该模块的序号**——所以本文档里出现 `04-` 这类前缀的图是正常的，它表示该流程归属 `04` 号模块文档）
- **图名固定为英文 slug**：即使本文档是中文，也先把流程名或章节语义名译成英文再命名（如 `下单流程` → `place-order-flow`），文件名不出现中日韩字符
- 本文档以**固定两行**引用该图，相对路径相对于本文档所在目录（`specs/design/`），不允许写绝对路径、不允许 `../` 跳转：
  - 第一行：`![<说明>](diagrams/<文档序号>-<图名>.<图类型>.svg)`
  - 第二行：`> [打开交互式版本](diagrams/<文档序号>-<图名>.<图类型>.html)`
  - **正文不得出现 `<svg>` 标签**（不得把 SVG 内容内联进正文）
- **校验不通过的图走占位形态（合法形态，不判缺陷）**：该图**不落三件套**，正文也**不写上面那两行**；改为在应放图的位置写一行固定占位：
  `> ⚠️ 占位：<图名> 未通过校验，原因：<诊断 code 与说明>（详见变更清单）`，并在变更清单的 `Diagrams` 列同步标 `未通过校验`。
  **既不落图、又不写这行占位说明**，才算缺陷。占位图的源 IR（`.json`）**必须从 `diagrams/` 移除**，不留孤儿源文件。
- 同一流程名出现在架构总纲与模块文档时，两处**共用同一组三件套**，且图类型必须一致——序号取**归属文档**，跨模块流程归架构总纲（`01-`）
- **单图主节点不超过 12**；复杂内容必须拆分成多张图分别落盘
